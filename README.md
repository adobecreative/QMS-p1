# QMS — نظام إدارة الجودة للمستشفى (سباهي · JCI)

نظام الجودة والاعتماد للمستشفى، مبني على **نفس هيكل منصة فكرة** (Portal-p2): نفس الألوان والواجهات، المستخدمين وصلاحية لكل نظام، الإعدادات، الترخيص، المساعد الذكي، البريد، والنسخ الاحتياطي. يعمل على Cloudflare (Workers + D1 + R2) مجانًا، أو على سيرفر داخل المملكة بـ `server/node.mjs`.

**موارد Cloudflare الخاصة بهذا المشروع** (منفصلة تمامًا عن منصة فكرة ونظام FMS):

| المورد | الاسم |
|---|---|
| Worker | `qms-p2` |
| قاعدة البيانات D1 | `qms-db-p2`، وللمعاينات `qms-db-p2-preview` |
| التخزين R2 | `qms-files-p2`، وللمعاينات `qms-files-p2-preview` |

> **نقل البيانات من موارد p1 (مرة واحدة):** قبل دمج تغيير الأسماء: `npx wrangler d1 export qms-db-p1 --remote --output qms.sql` ثم `npx wrangler d1 create qms-db-p2` ثم `npx wrangler d1 execute qms-db-p2 --remote --file qms.sql`. وأنشئ `qms-files-p2` وانسخ إليه ملفات `qms-files-p1` (R2 ← Data Migration). احذف موارد p1 بعد التأكد فقط.

إعداد النشر في Cloudflare (Workers & Pages ← المشروع ← Settings ← Build): **Build command فارغ**، و **Deploy command = `npx wrangler deploy`**، والفرع `main`.

**الترخيص:** الترخيص في `wrangler.jsonc` صادر لنطاق **`qms.ai-fikra.com`** (المستشفى العام، ينتهي 2027-11-04). اربط هذا النطاق بالـ Worker من Cloudflare: Workers & Pages ← qms-p2 ← Settings ← Domains & Routes ← Add ← Custom domain. أي نطاق آخر (مثل workers.dev) يظهر عليه «غير مرخّص».

**خطة الوحدات:** الأساس (هذه النسخة) ← فصول سباهي والمعايير ونسبة الجاهزية ← بلاغات OVR والشكاوى ← الإجراءات التصحيحية CAPA ← المؤشرات ولوحة الإدارة ← اللجان والاجتماعات. الوثائق والجولات والعقود والتقارير موجودة من المنصة وتُكيَّف للجودة.

## (من منصة فكرة) التوثيق الأصلي

# إدارة المرافق - متابعة الملفات والسياسات

نظام ويب لمتابعة ملفات الـ PDF (سياسة / برنامج / إجراء) حسب تاريخ الانتهاء، بثلاث صلاحيات، داشبورد بالألوان، قراءة الـ PDF داخل الصفحة، سجل نشاط، وتذكيرات بالبريد من Gmail. يعمل بالعربي والإنجليزي وعلى الموبايل.

> **نسخة التست:** هذا الريبو (`FMS-Managment-Test`) نسخة تجريبية منفصلة تمامًا عن المشروع الأصلي. الـ Worker اسمه `facilities-tracker-p2`، وقاعدة البيانات `facilities-db-p2`، والـ R2 `facilities-files-p2`. لا تضع هنا `database_id` الخاص بـ `facilities-db` الأصلية ولا اسم `facilities-tracker` أو `facilities-files`، وإلا ستكتب نسخة التست على بيانات المشروع الأصلي.

الاستضافة كلها على Cloudflare (الخطة المجانية): الموقع والـ API على Workers، البيانات على D1، وملفات الـ PDF على R2.

## المطلوب قبل البدء

- حساب Cloudflare (مجاني).
- كمبيوتر عليه Node.js إصدار 22 أو أحدث (النشر يتم من الكمبيوتر مرة واحدة، وبعدها النظام يعمل من أي جهاز).
- حساب Gmail يكون هو المُرسِل للتذكيرات.

## 1. النشر على Cloudflare

فك الضغط، افتح Terminal داخل فولدر المشروع، ونفّذ بالترتيب:

```bash
npm install
npx wrangler login
npx wrangler d1 create facilities-db
```

الأمر الأخير يطبع `database_id`. انسخه وضعه في ملف `wrangler.jsonc` مكان `PUT-YOUR-DATABASE-ID-HERE`. (لو سألك wrangler هل يضيف الإعداد للملف بنفسه، اختر لا، لأن الإعداد موجود.)

```bash
npx wrangler r2 bucket create facilities-files
npx wrangler deploy
```

- لو R2 غير مفعّل في حسابك، فعّله أولًا من لوحة Cloudflare (R2 Object Storage). التفعيل يطلب بطاقة دفع، لكن أول 10 جيجا مجانية.
- بعد `deploy` يظهر رابط النظام، بالشكل `https://facilities-tracker.<اسم-حسابك>.workers.dev`.
- الجداول تُنشأ تلقائيًا عند أول فتح للرابط، لا يوجد أمر إضافي.

## 2. أول دخول

افتح الرابط **فور النشر**. أول من يفتحه تظهر له صفحة "إعداد النظام لأول مرة" لإنشاء حساب السوبر أدمن، وبعدها تختفي هذه الصفحة نهائيًا.

ثم بالترتيب:

1. **الأقسام**: أضف الأقسام (اسم عربي + اسم إنجليزي).
2. **المستخدمون**: أضف أدمن لكل قسم واربطه بقسمه، وأضف المستخدمين العاديين.
3. **الداشبورد**: "إضافة ملف" لرفع الملفات.

## 3. إعداد مُرسِل البريد

1. افتح [script.google.com](https://script.google.com) بحساب Gmail المُرسِل، واختر New project.
2. امسح الكود الموجود والصق محتوى الملف `apps-script/Code.gs`.
3. غيّر قيمة `TOKEN` في أول الملف إلى رمز سري طويل من عندك، واحفظ.
4. Deploy ثم New deployment، النوع Web app، و Execute as: **Me**، و Who has access: **Anyone**. وافق على الصلاحيات.
5. انسخ رابط الـ Web app (ينتهي بـ `/exec`).
6. في النظام: **الإعدادات**، الصق الرابط والرمز السري نفسه، واحفظ.
7. اضغط "إرسال رسالة تجريبية لي" للتأكد.

لو عدّلت الكود في Apps Script بعد ذلك: Deploy ثم Manage deployments ثم Edit ثم New version.

حد Gmail العادي 100 مستلم في اليوم، وهو أكثر من كافٍ لأن كل أدمن تصله رسالة واحدة مجمّعة في اليوم.

### بديل: الإرسال من بريد على نطاق المؤسسة (Brevo)

لإرسال الرسائل من عنوان مثل `notifications@example.com` بدل Gmail:

1. أنشئ حسابًا مجانيًا على [brevo.com](https://www.brevo.com) (حتى 300 رسالة في اليوم).
2. **Senders, Domains & Dedicated IPs** ثم **Domains**: أضف النطاق، وأضف سجلات DNS التي يعطيها Brevo عند مزوّد النطاق (Cloudflare مثلًا). إن كان للنطاق سجل SPF من قبل، أضف إليه `include:spf.brevo.com` في السجل نفسه، ولا تنشئ سجل SPF ثانيًا.
3. **SMTP & API** ثم **API Keys**: أنشئ مفتاحًا (يبدأ بـ `xkeysib-`).
4. في النظام: **الإعدادات**، اختر طريقة الإرسال **Brevo**، والصق المفتاح، واكتب بريد المرسل (من النطاق الذي وثّقته)، واحفظ، ثم أرسل رسالة تجريبية.

إعدادات Gmail تبقى محفوظة؛ للرجوع إليها يكفي اختيار Gmail من جديد.

## كيف يعمل النظام

**البوابة والأنظمة**

بعد الدخول تظهر البوابة (Portal) وفيها الأنظمة اللي ليك صلاحية عليها:

- **إدارة الوثائق (Document Control):** الملفات والسياسات والتذكيرات وإقرار الاطلاع.
- **البلاغات وأوامر العمل (Requests & Work Orders):** بلاغات الموظفين لأي فريق.
- **مركز الإدارة (Admin Center):** المستخدمين، الأقسام، الموظفين، سجل النشاط، والإعدادات العامة (الشعار، البريد، النسخة الاحتياطية). للسوبر أدمن فقط.
- **إدارة الأصول (Asset Management):** قريبًا.

**الصلاحيات: حساب واحد لكل شخص، وصلاحية في كل نظام**

| النظام | الصلاحيات |
|---|---|
| الكل | سوبر أدمن: كل شيء في كل الأنظمة ومركز الإدارة |
| إدارة الوثائق | بدون دخول، قارئ (يتصفح ويقرأ كل الأقسام)، مسؤول وثائق القسم (يضيف ويعدّل ملفات قسمه فقط) |
| البلاغات وأوامر العمل | بدون دخول، متابعة بلاغات قسمه، فني / مهندس (يستلم ويقفل بلاغات فريقه)، مشرف فريق (يحوّل ويصعّد ويتابع فريقه) |

الحسابات اللي كانت موجودة قبل البوابة اتحولت لوحدها: أدمن القسم بقى مسؤول وثائق قسمه (ومشرف لو قسمه فريق)، والفني بقى فني وقارئ، والمستخدم بقى قارئ.

**الألوان (على مستوى كل ملف)**

- أخضر: ساري.
- أصفر: قرّب ينتهي. يبدأ قبل الانتهاء بعدد أيام (القيمة العامة من الإعدادات، ويمكن تغييرها لكل ملف).
- أحمر: منتهي.
- أبيض: تحت المراجعة (اختيار يدوي في الملف).
- بدون لون: ملف دائم، اختر "ملف دائم بدون تاريخ انتهاء".

**تجديد ملف منتهي**: من "تعديل" غيّر التواريخ واختر ملف PDF جديد. القديم يُحذف نهائيًا ولا يُحفظ، وسجل النشاط يسجّل من عدّل ومتى وما الذي تغيّر.

**التذكيرات**: تعمل يوميًا تلقائيًا، وتصل لأدمن القسم وللسوبر أدمن فقط:

- عند دخول الملف الأصفر، وعند دخوله الأحمر.
- تتكرر كل عدد أيام تحدده في الإعدادات طالما الملف أصفر أو أحمر (0 = مرة واحدة فقط).
- في تاريخ الإشعار المخصّص إذا حدّدته للملف.

**القراءة**: الـ PDF يُفتح داخل الصفحة (تنقّل بين الصفحات، تكبير، ملء الشاشة) بدون زر تنزيل.

**إقرار الاطلاع**: تحت كل ملف زر "قرأت وفهمت" يضغطه الموظف بعد القراءة. أدمن القسم والسوبر أدمن يرون عمود "الاطلاع" في الداشبورد (مثلًا 5 / 12)، وبالضغط عليه تظهر قائمة من قرأ ومتى ومن لم يقرأ بعد. عند رفع PDF جديد للملف يُطلب من الجميع قراءته من جديد.

**الهوية والشعار**: من "الإعدادات" يرفع السوبر أدمن شعار الجهة (PNG أو JPG أو WEBP أو SVG حتى 1 ميجابايت) ويكتب اسمها بالعربي والإنجليزي. يظهران تلقائيًا في أعلى كل الصفحات، وصفحة الدخول، وأيقونة المتصفح والشاشة الرئيسية للموبايل، ورسائل البريد، وعنوان تقرير Excel، بمقاسات تناسب الكمبيوتر والموبايل. بدون شعار يظهر الشكل الافتراضي. هذا يجعل النظام صالحًا لأي جهة بدون تعديل في الكود.

**البريد**: كل رسالة تصل بالعربية والإنجليزية معًا، وإعدادات البريد تظهر للسوبر أدمن فقط في مركز الإدارة.

**تقرير Excel**: زر "تصدير التقرير" في الداشبورد ينزّل ملف Excel حقيقي (‎.xlsx) بنفس الفلتر المعروض: الحالة بالألوان، التواريخ، الأيام المتبقية، ونسبة الاطلاع (للأدمن). الملف من اليمين لليسار، وبه فلاتر، ومضبوط للطباعة بالعرض.

## البلاغات وأوامر العمل

**الإعداد مرة واحدة (السوبر أدمن):**

1. من "الأقسام" علّم الأقسام اللي بتستقبل بلاغات كـ "فريق" (IT، البايوميد، الصيانة...).
2. من "المستخدمون" أضف الفنيين والمهندسين بصلاحية "فني" تحت فريقهم، والمشرف "أدمن قسم" على نفس الفريق.
3. من "البلاغات" ثم "أنواع المشاكل": كل نوع (جهاز طبي، كمبيوتر، تكييف...) يروح لفريق وله أولوية.
4. من "الموظفين" أضف الموظفين فرديًا أو ارفع ملف Excel (النموذج الجاهز فيه: الرقم الوظيفي، الاسم بالعربية، الاسم بالإنجليزية، القسم، الجوال). بمجرد وجود موظف نشط، يكتب الموظف رقمه الوظيفي فقط ويظهر اسمه وقسمه تلقائيًا، ولا يُقبل البلاغ إلا من رقم وظيفي نشط.
5. اختياري: من "الأماكن و QR" أضف الأماكن واطبع QR لكل مكان. ولو عايز البلاغ يكون من QR فقط فعّلها من الإعدادات.

**الموظف**: يفتح الرابط `/request` (أو يمسح الـ QR) بدون حساب، يكتب رقمه واسمه وقسمه ويختار نوع المشكلة، ويحصل على رابط متابعة. بعد القفل يقدر يقيّم أو يقول "المشكلة لسه موجودة" خلال 3 أيام.

**الفريق**: يستلم البلاغ ولازم يحدد وقت متوقع للحل، يعلّقه لو منتظر قطع غيار (وقت التعليق ما يتحسبش عليه)، يحوّله لفني أو لفريق آخر، ويقفله بنتيجة: اتحل، حل مؤقت، أو بدون حل مع السبب.

**الأولويات والتنبيهات**: P1 حرج لـ P4 منخفض، ولكل أولوية وقت استلام ووقت حل يتعدّلوا من الإعدادات. "يؤثر على مريض" يرفع الأولوية درجة. كل 15 دقيقة يتم الفحص: لو عدّى الوقت يتبعت بريد للفني والمشرف، ولو عدّى الضعف يتصعّد للسوبر أدمن.

**المساعد الذكي والأتمتة**: يقترح المساعد نوع العطل من وصف الموظف. يعمل مجانًا عبر Cloudflare Workers AI دون أي إعداد، وحده اليومي في إعدادات مركز الإدارة. ومن صفحة الأقسام يمكن تفعيل "التوزيع التلقائي" لأي فريق، فيُسند كل بلاغ جديد للفني الأقل ضغطًا. ويُنبَّه المشرف تلقائيًا عند تكرار العطل نفسه في الموقع نفسه 3 مرات خلال 30 يومًا، وعند أي تقييم بنجمتين أو أقل.

**التقرير**: زر "تصدير التقرير" في صفحة البلاغات ينزّل Excel بكل البلاغات وأوقات الاستلام والحل والالتزام بالوقت والتقييم.

## إدارة الأصول والصيانة الوقائية

**الإعداد:** من "المستخدمون" أعطِ مسؤول الأصول (مثل مشرف الهندسة الطبية) صلاحية "مدير الأصول"، ومن يحتاج الاطلاع فقط صلاحية "اطّلاع".

**سجل الأصول:** أضف الأجهزة واحدًا واحدًا أو ارفعها من Excel (زر "تحميل نموذج Excel" يعطيك الأعمدة). لكل جهاز رقم أصل ونوع جهاز. أنواع الأجهزة (جهاز تنفس، مضخة محاليل، مكيف...) لها صفحة خاصة في إدارة الأصول، وكل نوع مرتبط بالفريق المسؤول عن صيانته، وتأتي الأنواع الشائعة جاهزة. في صفحة الجهاز تظهر بياناته وخطط صيانته وسجل ما نُفّذ وكل البلاغات عليه، ويمكن طباعة QR خاص به يفتح نموذج البلاغ ورقم الجهاز معبأ.

**خطط الصيانة:** لكل جهاز خطة صيانة وقائية وخطة معايرة وخطة فحص سلامة، ولكل خطة تكرار (كل كم شهر) وموعد قادم وبنود عمل. قبل الموعد بعدد أيام تحدده (7 افتراضيًا) يصدر أمر عمل تلقائيًا في نظام البلاغات لفريق الجهاز تحت نوع "صيانة مجدولة"، وعند إغلاقه ينتقل الموعد القادم تلقائيًا.

**جدول الصيانة:** يعرض كل الخطط حسب موعدها (المتأخرة، وما يحل خلال 30 يومًا، والأوامر المفتوحة) مع نسبة الالتزام بالمواعيد خلال آخر سنة.

## جولات التفتيش

**الإعداد:** من "المستخدمون" أعطِ مسؤول السلامة أو الجودة صلاحية "مدير الجولات"، والمفتشين صلاحية "مفتش".

**قوائم الفحص:** لكل قائمة اسم وبنود (مثل: طفاية الحريق في مكانها وصالحة) وأماكن وتكرار بالأيام، ونوع عطل يُستخدم للبنود المخالفة.

**تنفيذ الجولة:** يفتح المفتش «الجولات المستحقة» من الجوال، ويختار المكان، ويضع لكل بند سليم أو مخالف أو لا ينطبق. البند المخالف يحتاج وصفًا للمشكلة. عند الحفظ يصدر بلاغ واحد بكل البنود المخالفة لفريق نوع العطل، وينتقل موعد المكان إلى الجولة القادمة.

**السجل:** كل الجولات المنفذة بتاريخها والمفتش ونتيجتها والبلاغ الذي صدر عنها، مع نسبة الالتزام بالمواعيد.

**مسح رمز المكان:** رمز QR المطبوع من صفحة الأماكن يعرض خيارين إذا كان للمكان جولات: طلب صيانة أو جولة تفتيش. المفتش يمسحه فتفتح جولة هذا المكان، وتُسجَّل الجولة "بمسح رمز المكان". ويمكن من صفحة قوائم الفحص إلزام المسح، فلا تُحفظ جولة بدونه.

**التذكير:** كل صباح يصل للمفتشين ومدير الجولات إيميل بالجولات المستحقة اليوم والمتأخرة. يُشغّل ويُوقف من صفحة قوائم الفحص، ويحتاج إعداد مُرسِل البريد.

## العقود والموردين
داخل إدارة الأصول: سجل الموردين بوثائقهم الرسمية (السجل التجاري، والزكاة، والتأمينات، وترخيص هيئة الغذاء والدواء، والتأمين) مع تاريخ انتهاء كل وثيقة. والعقود بقيمتها ومدتها وملفها، والأجهزة المشمولة بها، والزيارات الوقائية المتفق عليها، وزمن الحضور والغرامة عن كل ساعة تأخير. الفني يحوّل البلاغ للمورد ويسجل وقت حضوره، والنظام يحسب التأخير والغرامة ويقيّم كل مورد. يصل لمديري الأصول تنبيه بالبريد قبل انتهاء العقد بـ 90 و60 و30 يومًا، وقبل انتهاء وثائق الموردين.

## المخزون وقطع الغيار
داخل إدارة الأصول، وله ثلاث طرق يختارها مدير النظام:
- **مخزون مستقل:** كل شيء هنا، من الشراء والاستلام إلى الصرف والجرد.
- **مخزن فرعي مرتبط بنظام ERP:** المستودع الرئيسي في ERP، والتحويلات والمشتريات تصل عبر الواجهة البرمجية.
- **المخزون في نظام ERP:** الفني يطلب القطعة، ويصرفها نظام ERP، ثم تُسجَّل على البلاغ.

الفني يصرف القطعة على البلاغ ويُرجع ما لم يُستخدم. وعند بلوغ الحد الأدنى يُفتح طلب احتياج، ويصل تنبيه لمديري الأصول.

صفحة "تكلفة الصيانة" تعرض تكلفة القطع حسب القسم ومركز التكلفة وحسب الجهاز. القطع المشمولة بعقد مورد تُحمّل على المورد. لا تُسجَّل قيود محاسبية هنا، ويأخذ النظام المالي الأرقام عبر الواجهة البرمجية أو ملف Excel.

## التقارير والمؤشرات
لمدير النظام: تقرير شهري في صفحة واحدة يضم البلاغات (الجديدة والمغلقة، والالتزام بأوقات الاستلام والإغلاق، ومتوسط الأوقات، والتقييم)، وتوزيعها حسب الفريق والأعطال والأماكن والأقسام، واتجاه آخر 6 أشهر، والصيانة الوقائية والجولات والوثائق. كل رقم بجانبه رقم الشهر السابق، ويمكن اختيار أي شهر من آخر سنة وطباعة التقرير.

## الربط مع الأنظمة الأخرى (API)
من مركز الإدارة ← الربط (API): أنشئ مفتاحًا لكل نظام (مثل الموارد البشرية أو نظام المستشفى) وامنحه الصلاحيات التي يحتاجها فقط. يظهر المفتاح مرة واحدة. الصفحة نفسها فيها دليل الاستخدام والأمثلة: مزامنة قائمة الموظفين، وفتح بلاغ صيانة، ومتابعة البلاغات، وقراءة سجل الأصول، على العنوان `/api/v1`.

## العمل بدون إنترنت
إذا انقطع الإنترنت يبقى النظام مفتوحًا على الأجهزة التي استُخدمت قبل الانقطاع. تظهر الصفحات بآخر نسخة محفوظة على الجهاز، ويمكن تسجيل بلاغات وإجراءات وأصول وخطط صيانة، وتُحفظ على الجهاز وتُرسل تلقائيًا عند عودة الاتصال. يظهر شريط أعلى الصفحة يوضح حالة الاتصال وعدد الإدخالات المنتظرة.

## ملاحظات مهمة

- **وقت التذكير اليومي**: مضبوط على 05:00 بتوقيت UTC (تقريبًا 8 صباحًا بتوقيت القاهرة والرياض). لتغييره عدّل `crons` في `wrangler.jsonc` ثم `npx wrangler deploy`. والمنطقة الزمنية المستخدمة في حساب الأيام تُغيَّر من صفحة الإعدادات.
- **الملفات**: PDF فقط، وبحد أقصى 25 ميجابايت للملف.
- **عدم وجود زر تنزيل لا يمنع النسخ تمامًا**: أي شخص يستطيع قراءة ملف يستطيع تقنيًا حفظه أو تصويره. لا تعتمد على ذلك كحماية للملفات السرية.
- **كلمات المرور**: 8 أحرف على الأقل، والحساب يُقفل 15 دقيقة بعد 5 محاولات خاطئة. عدد دورات التشفير (`PBKDF2_ITERATIONS` في `src/worker.js`) مضبوط على 20000 ليناسب حدود الخطة المجانية، ويمكن رفعه على الخطة المدفوعة.
- **التحقق بخطوتين**: كل مستخدم يفعّله من زر حسابه أعلى الصفحة بتطبيق مصادقة على الهاتف (Google Authenticator أو Microsoft Authenticator)، ويحصل على 10 رموز استرداد تظهر مرة واحدة. من مركز الإدارة ← الإعدادات ← أمان الدخول يمكن جعله إلزاميًا لمديري النظام أو لكل المديرين (فعّله لحسابك أولًا). من فقد هاتفه ورموزه يعيد السوبر أدمن ضبطه من صفحة المستخدمين. كل عمليات الدخول والمحاولات الخاطئة تظهر في سجل النشاط.
- **الترخيص**: يعمل النظام فقط على النطاقات المذكورة في الترخيص الموضوع في `wrangler.jsonc` تحت `vars.LICENSE`. للتجديد استبدله بالترخيص الجديد وادمج. قبل الانتهاء بـ 30 يومًا يظهر تنبيه لمدير النظام، وبعد الانتهاء يعمل 30 يومًا ثم يصبح للقراءة فقط حتى التجديد، دون فقد أي بيانات.
- **مالك النظام**: أول حساب يُنشأ من صفحة "إعداد النظام لأول مرة" هو المالك. لا يظهر في قائمة المستخدمين لأي سوبر أدمن آخر، ولا يستطيع أحد غيره تعديله أو إيقافه أو حذفه. المالك يرى الجميع ويتحكم في الجميع. (أفعاله تظهر باسمه في سجل النشاط.)
- **نسيان كلمة المرور**: من صفحة الدخول "نسيت كلمة المرور؟" يصل للمستخدم رابط بالبريد صالح 30 دقيقة ولمرة واحدة (حد أقصى 3 طلبات في الساعة لكل حساب). الرد واحد سواء كان البريد مسجّلًا أم لا. تغيير كلمة المرور يغلق كل الجلسات المفتوحة ويُسجَّل في سجل النشاط. يحتاج إعداد مُرسِل Gmail. والسوبر أدمن يستطيع أيضًا وضع كلمة مرور جديدة لأي مستخدم من صفحة المستخدمين.
- **تغيير النصوص**: كل نصوص الواجهة في `public/i18n.js`.
- **النسخة الاحتياطية**: من "الإعدادات" زر "تنزيل نسخة احتياطية كاملة" (للسوبر أدمن) ينزّل ملف ZIP فيه backup.json بكل البيانات (بدون كلمات المرور) وكل ملفات الـ PDF في فولدر لكل قسم. يُنصح بها شهريًا. وCloudflare يحتفظ تلقائيًا بتاريخ قاعدة البيانات آخر 7 أيام (Time Travel). وللتقنيين: `npx wrangler d1 export facilities-db --remote --output backup.sql`
- **استرجاع نسخة احتياطية** (تجربة الاسترجاع تُشغَّل تلقائيًا في الاختبارات على كل تعديل، `tests/ci/restore.mjs`):
  1. أنشئ قاعدة D1 فارغة واربطها بالنظام، ثم افتح الموقع مرة واحدة حتى تُبنى الجداول.
  2. خذ `backup.json`، إما من الملف المضغوط المنزَّل من الإعدادات، أو من مرفق البريد الأسبوعي.
  3. حوّله إلى SQL بالأمر: `OWNER_PASSWORD='كلمة مرور جديدة' node tools/restore-sql.mjs backup.json > restore.sql`
  4. طبّقه بالأمر: `npx wrangler d1 execute <اسم القاعدة> --remote --file restore.sql`
  5. يدخل المالك بكلمة المرور الجديدة، ثم يضبط البريد من الإعدادات، لأن مفاتيح البريد لا تُحفظ في النسخة. بعد ذلك يستخدم باقي المستخدمين "نسيت كلمة المرور".
  6. **ما لا يرجع:** التحقق بخطوتين، والجلسات، وتنبيهات الموبايل، ومفاتيح الـ API، وروابط متابعة البلاغات القديمة عند الموظفين، والنص المستخرج من ملفات PDF للبحث. ملفات الـ PDF نفسها تبقى في R2، أو تُرفع من الملف المضغوط.
- **تحديث النظام بعد أي تعديل في الكود**: `npx wrangler deploy`

## التشغيل على سيرفر عادي (استضافة داخل المملكة)

يمكن تشغيل النظام نفسه، بالكود نفسه، على أي سيرفر عليه Node.js، سواء كان سحابة سعودية أو سيرفرًا لدى الجهة، دون الحاجة إلى Cloudflare. تُحفظ قاعدة البيانات في ملف SQLite، وتُحفظ ملفات الـ PDF في مجلد على قرص السيرفر نفسه، أو في تخزين متوافق مع S3 عند الرغبة. وتُشغَّل كل الاختبارات على هذه النسخة أيضًا مع كل تعديل (`tests/ci/run-node.sh` و`run-s3.sh` و`run-docker.sh`).

### الطريقة الأسهل: Docker

على سيرفر عليه Docker، وبعد توجيه النطاق (DNS) إلى عنوان السيرفر:

```bash
cd deploy
cp example.env .env      # ثم اكتب فيه النطاق والترخيص
docker compose up -d --build
```

يعمل النظام على `https://<النطاق>` بشهادة SSL تُصدر وتُجدَّد تلقائيًا، ويعود للعمل وحده بعد إعادة تشغيل السيرفر. وتبقى البيانات في وحدة التخزين `portal-data` عند التحديث. للتحديث بعد أي تعديل في الكود: `git pull` ثم الأمر نفسه `docker compose up -d --build`.

### بدون Docker

**المتطلبات:** Node.js الإصدار 22 أو أحدث. لا يحتاج إلى `npm install`.

**التشغيل:**

```bash
LICENSE='PORTAL1...' DATA_DIR=/var/lib/portal PORT=8080 node server/node.mjs
```

| المتغير | الوظيفة |
|---|---|
| `PORT` | المنفذ (الافتراضي 8787) |
| `HOST` | العنوان (الافتراضي 0.0.0.0) |
| `DATA_DIR` | مجلد البيانات: فيه `portal.db` ومجلد `files` (الافتراضي `data/`) |
| `LICENSE` | الترخيص، ويجب أن يشمل نطاق هذا السيرفر |
| `TRUST_PROXY` | ضعه `1` إذا كان السيرفر خلف nginx أو موزّع أحمال، ليُسجَّل عنوان المستخدم الحقيقي |
| `S3_ENDPOINT` `S3_BUCKET` `S3_ACCESS_KEY` `S3_SECRET_KEY` `S3_REGION` | اختيارية: لحفظ ملفات الـ PDF في تخزين متوافق مع S3 بدل قرص السيرفر (مثل Oracle Object Storage في جدة أو الرياض، أو Google Cloud Storage في الدمام، أو MinIO لدى الجهة). قاعدة البيانات تبقى في `DATA_DIR` |

- **HTTPS:** ضع أمامه nginx أو Caddy بشهادة SSL، ووجّهه إلى المنفذ، وفعّل `TRUST_PROXY=1`. الدخول والتنبيهات تحتاج HTTPS.
- **التشغيل الدائم:** شغّله خدمةً في systemd (`Restart=always`) حتى يعود تلقائيًا بعد إعادة تشغيل السيرفر.
- **المهام المجدولة:** التذكير اليومي (05:00 UTC) والمهام كل 15 دقيقة والنسخة الأسبوعية تعمل من داخل البرنامج نفسه، ولا تحتاج cron.
- **النسخ الاحتياطي:** إضافة إلى النسخة الأسبوعية بالبريد، انسخ مجلد `DATA_DIR` كاملًا يوميًا إلى مكان آخر. وللاسترجاع اتبع خطوات "استرجاع نسخة احتياطية" أعلاه، مع تطبيق الخطوة 4 هكذا والبرنامج متوقف: `DATA_DIR=/var/lib/portal node server/apply-sql.mjs restore.sql`
- **ما لا يتوفر في هذه النسخة:** المساعد الذكي (تصنيف البلاغات بالذكاء الاصطناعي) يبقى متوقفًا، لأنه من خدمات Cloudflare. وباقي النظام يعمل كاملًا.

## التجربة على الكمبيوتر قبل النشر (اختياري)

```bash
npm install
npm run dev
```

ثم افتح `http://localhost:8787`. البيانات هنا محلية ومنفصلة عن النسخة المنشورة.

## محتويات المشروع

```
wrangler.jsonc         إعدادات Cloudflare
src/worker.js          الـ API والصلاحيات ومهمة التذكير اليومية
server/node.mjs        التشغيل على سيرفر عادي بـ Node.js بدل Cloudflare (و s3.mjs للتخزين على S3)
Dockerfile, deploy/    التركيب بـ Docker مع HTTPS تلقائي
public/                الواجهة (index.html, app.js, styles.css, i18n.js)
public/vendor/         مكتبة PDF.js لعرض الملفات
apps-script/Code.gs    سكريبت الإرسال من Gmail
tests/                 سكريبتات الاختبار (لا تُنشر مع النظام)
demo/                  مصدر النسخة التجريبية (لا تُنشر مع النظام)
HANDOFF.md             ملف التسليم: تاريخ المشروع وقراراته وتفاصيله، لإكمال العمل في محادثة جديدة
```
